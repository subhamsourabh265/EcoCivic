# EcoCivic Build Plan

Build EcoCivic in small, working increments. Each phase should leave you with something you can run, demonstrate, test, and explain in an interview.

Phases 1 and 2 are implemented: workspace tooling and CI, a React/Vite shell, an integrated Issues package, browser-persisted mock reports, URL filters, report details and timelines, validated report creation, and component/integration tests. Module Federation is next; backend services and real authentication remain future work.

## 1. Establish the development foundation

- Initialize a **pnpm workspace** for `apps/*`, `services/*`, and `packages/*`.
- Configure shared TypeScript settings, ESLint, Prettier, and Node/package-manager versions.
- Add root commands for development, builds, linting, type checking, and tests.
- Document environment variables using `.env.example`.
- Create a basic GitHub Actions workflow for linting, type checking, and builds.

**Done when:** a fresh checkout can install dependencies and run consistent checks.

## 2. Build the shell and Issues UI

Start with React, TypeScript, and Vite. Keep Issues integrated into the shell initially; introduce federation after the feature works.

Implement:

- Global navigation, layout, and routing.
- Issue feed with category, severity, and status filters.
- Issue details with a status timeline.
- Report creation with validation.
- Loading, empty, error, and successful submission states.
- Responsive layouts and accessible forms.

Use synthetic fixtures through a mock API layer. Introduce TanStack Query for API data and keep form state local. Add Zustand only when a concrete shared UI state requirement appears.

**Done when:** a user can create a mock report, find it in the feed, and inspect its details.

## 3. Introduce Module Federation

- Turn `issues-mfe` into a separately running remote.
- Make the shell load it through a defined integration contract.
- Add Community and Analytics remotes with minimal landing pages.
- Configure shared React dependencies.
- Establish routing ownership and authentication integration.
- Support environment-specific remote URLs.
- Add loading boundaries and recovery when a remote is unavailable.
- Give each application its own build command.

Keep shared packages small: independently deployed MFEs still need compatible contracts.

**Done when:** you can rebuild and serve one remote independently, and a failed remote does not break global navigation.

## 4. Build a persistent backend vertical slice

Use **NestJS + PostgreSQL**, choosing one ORM before implementation.

Start with `api-gateway` and `issue-service`:

- Define issue categories, severity levels, and lifecycle transitions.
- Implement DTO validation, controllers, services, and repositories.
- Add migrations and development seed data.
- Implement create, list, and detail endpoints.
- Add pagination, filtering, consistent errors, and API documentation.
- Connect the Issues UI to the real API.
- Add request IDs, structured logs, and health endpoints.

Use a clearly isolated development identity until authentication is implemented.

**Done when:** a report created in the browser persists across restarts and is retrieved through the gateway.

## 5. Add authentication and authorization

Integrate an external OIDC provider and implement the identity service for profiles and application roles.

Before coding, record the browser authentication decision: a backend-for-frontend with a secure session cookie, or a browser OIDC client using Authorization Code with PKCE.

Then implement:

- Login, logout, session expiry, and protected routes.
- JWT validation where access tokens are accepted.
- Backend permissions for citizens, moderators, authorities, NGOs, and administrators.
- Ownership checks and authorized status transitions.
- Audit records for moderation and status changes.
- Appropriate CORS, CSP, security headers, rate limits, and CSRF protection where cookies authenticate requests.

**Done when:** a citizen cannot invoke moderator or authority actions, even by calling the API directly.

## 6. Complete the civic reporting workflow

Add features in this order:

1. Confirm an issue, enforcing one confirmation per user.
2. Comment on an issue.
3. Verify or reject a report as a moderator.
4. Accept and progress an issue as an authority.
5. Resolve it with resolution notes and an after-photo.
6. Suggest nearby existing reports before creating a duplicate.

For uploads, use object storage with file size/type validation and controlled access. Decide how precise public location data should be.

**Done when:** multiple users can complete the full report-to-resolution journey with a reliable audit trail.

## 7. Build community participation

Expand `community-mfe` with:

- Local initiatives and volunteering.
- Joining and leaving an initiative.
- Community challenges and participation history.
- Moderation and abuse-reporting controls.

Keep confirmations and issue comments in the issue service initially. Introduce a dedicated community service when initiative ownership and deployment needs justify it.

**Done when:** users can organize and participate in a local activity linked to a meaningful community outcome.

## 8. Add analytics and environmental impact

Implement `impact-service` and `analytics-mfe` with:

- Reports by category and area.
- Resolution rates and time to resolution.
- Open issues by age and severity.
- Community participation.
- Verified environmental outcomes.

Define every metric before displaying it. Resolving one water-leak report does not establish how many litres were saved; estimates need explicit assumptions and labels.

**Done when:** dashboard totals are traceable to stored records and documented calculations.

## 9. Strengthen testing and delivery

Write relevant tests throughout earlier phases; use this phase to complete coverage across boundaries.

| Layer               | Main focus                                                  |
| ------------------- | ----------------------------------------------------------- |
| Unit                | Permissions, lifecycle rules, metric calculations           |
| React component     | Forms, errors, interactions, accessibility                  |
| Backend integration | Validation, database constraints, authorization             |
| Contract            | API compatibility between independently released components |
| Playwright          | Citizen → moderator → authority workflow                    |

Then add:

- Container builds and local Docker Compose.
- CI checks scoped to affected apps and their shared dependencies.
- Dependency and container scanning.
- Independently versioned deployment artifacts.
- Staging smoke tests and a rollback procedure.

**Done when:** a pull request validates affected components and a release can be deployed and rolled back predictably.

## 10. Deploy to one cloud

Choose **Azure or GCP** and establish a working staging deployment before adding every infrastructure abstraction.

- Serve frontend artifacts through static hosting and a CDN.
- Deploy backend containers.
- Provision managed PostgreSQL, object storage, and secret management.
- Configure HTTPS, domains, backups, and environment separation.
- Introduce Terraform for repeatable provisioning.
- Add Kubernetes and Helm as the next deployment milestone.
- Choose Helm or Kustomize as the primary application configuration approach.

**Done when:** the system runs on a public staging URL, infrastructure is reproducible, and database restoration has been exercised.

## 11. Measure performance and resilience

- Collect logs, metrics, and distributed traces.
- Define availability and latency objectives.
- Measure LCP, INP, CLS, bundle size, and API latency.
- Investigate slow database queries and add justified indexes.
- Optimize images, pagination, route loading, and expensive rendering.
- Add caching with explicit invalidation rules.
- Test timeouts, unavailable remotes, backend failures, and recovery.
- Add actionable alerts and operational runbooks.

**Done when:** you can demonstrate a measured bottleneck, its improvement, and how the system behaves during a failure.

## 12. Introduce events, then optional GenAI

For events:

- Publish versioned issue lifecycle events.
- Use a transactional outbox to avoid database/event dual-write failures.
- Introduce Kafka consumers for impact projections and notifications.
- Implement idempotency, retries, dead-letter handling, and replay.
- Expose eventual consistency clearly in the UI.

For GenAI, start with an assistive feature such as category suggestions or duplicate candidates. Establish evaluation data, privacy controls, human review, and a fallback before release.

**Done when:** replaying an event cannot double-count impact, and AI suggestions remain reviewable.

## Interview preparation and first milestone

For interview preparation, accompany each phase with a short architecture decision record, a demo, test evidence, and an explanation of the tradeoffs.

**Start with Phase 1, then deliver the first working slice: shell → report form → issue feed → issue details.**
